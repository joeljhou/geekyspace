::: tip 核心观点

**代码评审（Code Review，CR）不仅是找 Bug，更是研发协同、知识传承和统一代码质量的重要载体。**

高质量评审需要评审者认真审查，也需要开发者积极配合；通过尽早发起、聚焦变更，降低成本、提高收益。
:::

## 1. 为什么要代码评审？

代码评审是提高代码质量的重要途径之一，与测试、静态分析和持续集成互为补充，也能帮助提高一致性、降低协同成本、促进知识共享。

### 1.1 背景、问题、目标

**代码是写给人看的，不是写给机器看的，只是顺便计算机可以执行而已。**

团队协作中，缺少有效评审机制容易带来以下问题：

1. **一致性下降**：编码风格与实现方式各异，理解、协同成本上升
2. **重复代码泛滥**：大量重复逻辑的代码，修改成本倍增
3. **指导缺位**：开发者缺少编码指导及经验分享渠道
4. **缺乏监督**：研发行为愈发随意
5. **问题后置**：线上问题难以提前发现

| 评审维度 | 关注点 |
| --- | --- |

## 2. 怎样做好代码评审

> 开发者可以通过一些行为降低评审者的时间成本：小变更、明确的标题、详细的描述；评审者针对代码、不针对作者，不情绪化，不过度追求完美。

认可价值不等于能落地：**组织**上缺评审文化、制度与激励，有人认真有人随意，形成“破窗效应”；**执行**上评审成本过高、缺少方法，最后只剩“看过、同意”。因此落地需要两端配合——评审者认真审查，开发者主动降低评审成本。

### 2.1 开发者角度：主动降低评审成本

#### 秘诀 1：发起评审的时机越早越好

越早发现问题，修改意愿越高，返工成本越低。

| 发起时机 | 特点 |
| --- | --- |
| **代码 Push 时** | 平台可自动触发评审，最早进入他人视野 |
| **创建变更、进入集成测试时** | 早发现问题，容易安排调整 |
| **临发布才评审** | 修改可能要求重测重联调，发布压力让评审走过场 |

#### 秘诀 2：让每次变更只做一件事

Code Review 是“开发习惯”而非“盖章动作”：只有每次提交尽可能小而独立，他人才可能真正帮你 review，从而有效控制评审成本。以下“顺手”场景不可取：

1. 顺手修改与本需求无关的变量命名
2. 顺手重构与本需求无关的 Method
3. 顺手格式化历史上不规范的整个文件

#### 秘诀 3：编写语义明确的标题

标题是评审者最先接触的信息，评审前要让对方了解本次变更解决的问题。建议按团队约定格式编写：

| 变更类型 | 标题格式 |
| --- | --- |
| 修复线上 Bug | `fix(模块): 简单描述` |
| 修复线上紧急 Bug | `紧急fix(模块): 简单描述` |
| 上线新 Feature | `feature(模块): 简单描述` |

#### 秘诀 4：编写详细的描述

描述应介绍本次改动的**需求背景、改动范围及影响点**。一段清晰的描述能让评审者快速理解背景、直接开始评审，降低沟通成本。

#### 秘诀 5：把风格问题交给自动化扫描

每个人的代码风格各异，把大量精力花在纠正代码风格上不理智。风格问题交给自动化：风格扫描、代码规约扫描插件（如 ESLint、P3C、国际化扫描），在代码平台配置扫描任务并设置卡点。

### 2.2 评审者角度：认真审查、对事不对人

把评审代码作为工作的一部分，留出专门的时间完成、及时响应，避免阻塞他人。发表评论时：

1. **针对代码，不要针对作者**：讨论“这段代码的问题”，而不是“你的问题”
2. **避免过度追求完美**：区分“必须解决”与“可以接受”，不因小瑕疵反复阻塞
3. **明确评论是否需要解决**：注明是建议、疑问还是必须修改
4. **建议给出明确论据或编码示例**：让作者理解“为什么”，而不只是“改什么”
5. **不要吝啬赞美**：好的实现同样值得指出，正向反馈让评审更可持续
6. **态度谦和，不情绪化**：评审是协作，不是审判

## 4. 回顾

> **有效评审不是多一道签字，而是在问题仍容易修改时，让合适的人共同理解并改进代码。**

- **评什么**：实现逻辑（实现、逻辑、测试、安全、风险、性能）＋ 代码质量（规范、可测性、可读性、重复度、可维护性）
- **开发者**：尽早发起、变更小而独立、标题语义明确、描述详细、风格交给自动化
- **评审者**：针对代码不对人、不过度追求完美、评论明确可执行、给出论据与示例、不吝赞美、态度谦和
- **组织**：文化、制度与激励并行，避免“破窗效应”与走过场
