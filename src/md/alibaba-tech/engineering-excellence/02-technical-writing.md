## 1. 为什么要写？

**背景、问题、目标**

1. **背景：从个人开发走向团队协作。** 需求、实现、依赖、系统边界和研发人员持续变化，软件复杂度随之上升。
2. **问题：** 缺少有效文档，团队就会陷入：
	- **知识靠口传**：历史决策不透明，重复答疑、高频咨询打断研发。
	- **有文档也难用**：内容陈旧、结构混乱、描述错误，接入与维护仍依赖找人。
	- **知识难沉淀**：没有评审、责任人和统一入口，质量与可检索性缺乏保障。
3. **目标：把文档与代码共同作为研发交付物，降低理解、协作和维护成本。**

![技术文档与代码协同支撑持续迭代](https://img.geekyspace.cn/pictures/2026/202610292201262.png)

**核心价值**

- **解释系统**：让读者理解架构、流程、边界及重要设计决策。
- **支持演进**：记录关键变化与背景，减少人员更替造成的知识流失。
- **促进复用**：沉淀团队知识，方便分享、学习和接入。
- **反哺思考**：通过写作梳理逻辑、发现设计漏洞，形成后续改进方向。

**意义**：写技术文档可以帮助团队完成**当前的信息共享**和**长期的技术知识传承**！！！

## 2. 如何写好？

### 2.1 特征

好的技术文档应具备的特征：**目标明确、结构清晰、表达准确、经过评审、持续保鲜。**
落到团队实践，重点抓四件事：

1. **目标**：明确研究对象、读者和问题边界。
2. **结构**：按文档类型统一模板，同类内容归组，术语与表达保持一致。
3. **评审**：建立变更与反馈机制，既审表达，也审技术可行性。
4. **Owner**：明确责任人，做好版本管理，随系统变化持续更新。

![好技术文档的特征与保障机制](https://img.geekyspace.cn/pictures/2026/202610292215051.png)

### 2.2 动笔前的 5W

1. **`Why`｜为什么写**：及时获取有价值的技术反馈，促进技术探讨与沟通。
2. **`Who`｜谁来读**：面向技术人员阅读与评审，明确具体受众。
3. **`What`｜有什么用**：明确文档的用途与目的，据此搭建内容框架。
4. **`When`｜何时创建、评审和更新**：记录关键日期，便于读者判断时效，避免使用过期信息。
5. **`Where`｜放在哪里**：团队统一存放，保持稳定地址并管理版本；可关联产品需求，在核心代码中添加文档指引。

### 2.3 六个阶段

1. **准备（`Prepare`）：明确需求、受众与范围**
   - **盘点需求**：为什么写，期望达到什么目的。
   - **明确受众**：开发人员与普通用户关注点不同，内容深度和组织方式也应不同。
   - **界定范围**：确定覆盖哪些内容或模块，让资料搜集和写作有所侧重。

2. **调研（`Research`）：收集证据，说明取舍**
   - **借鉴而非照搬**：对比多个有代表性的同类文档，学习组织方式，形成初步框架。
   - **多渠道搜集资料**：结合网络搜索、问卷、访谈、实验，以及邮件讨论、分析报告和技术文章；具体案例要具体分析与验证。
   - **记录选型依据**：写清各项取舍（`Trade-off`）的成本（`Cost`）、收益（`Benefit`）与风险（`Risk`），让后来者能理解当时的决策意图。

3. **构建（`Organize`）：用金字塔结构搭提纲**
   - **纵向展开**：结论先行、以上统下，从中心观点逐层展开支撑观点与论据。
   - **横向组织**：同类内容归组，按逻辑递进，避免同一层级混杂不同维度。
   - **选择表达方式**：参考同类模板；用图解释关系与流程，用表呈现对比与数据，不为装饰而配图表。

4. **撰写（`Write`）：准确表达，边写边改**
   - **语言规范**：语法正确、措辞得体、术语一致，减少口语和无意义修饰。
   - **保持专注**：及时修正发现的问题，减少后续返工。
   - **检查内容**：文题是否相符，逻辑是否连贯，有无缺漏、赘余或需要重组的内容。

5. **审阅（`Review`）：先自审，再评审与修订**
   - **区分审阅重点**：语言审阅检查表达是否简洁得体；技术审阅检查描述是否正确、方案是否可行、论据是否充分。
   - **提前预读**：评审前发送文档，必要时先单独沟通争议，让会议聚焦关键问题。
   - **及时处理反馈**：判断后修订；不明确的问题先讨论或验证，再次评审。审阅与修订可能反复多轮。

6. **发布（`Release`）：统一沉淀，持续维护**
   - **发布归档**：将阶段性成果放入统一知识空间，明确 Owner，管理版本与变更记录。
   - **持续保鲜**：随系统变化更新内容，重要变更按需再次评审，避免过期信息误导读者。

**六阶段是迭代过程，不是一次性流水线。** 评审可能要求补充调研或调整结构，发布后仍需维护。

## 3. 技术文档分类

### 3.1 常见文档框架

**先明确文档服务谁、解决什么问题，再选择对应模板。** 常见文档分为两类：

1. **平台与产品文档：帮助用户使用产品**
   - **使用与管理**：用户指南、管理员指南、操作指南。
   - **排障与参考**：故障诊断、FAQ、版本说明。
   - **学习与理解**：案例分析、技术白皮书。
2. **业务交付文档：帮助团队设计、实现与维护系统**
   - **架构层**：业务架构、技术架构、应用架构、数据架构。
   - **设计层**：工程结构、模块设计、代码设计、API 接口文档。
   - **运行层**：技术运维文档。

![技术文档分类：平台产品文档与业务交付文档](https://img.geekyspace.cn/pictures/2026/202610292243915.png)

**以详细技术方案为例**，可按以下提纲组织（根据课程整理，非原模板逐字复刻）：

1. **背景与目标**：为什么做，要解决什么问题，本次范围是什么？
2. **调研与选型**：有哪些备选方案，如何权衡成本、收益与风险？
3. **架构与设计**：系统边界、模块职责、依赖关系和关键流程是什么？
4. **风险与约束**：如何应对稳定性、安全、数据安全及合规要求？
5. **评审与修订**：形成了哪些结论，还有哪些问题待验证？

**模板是检查遗漏的工具，不是固定答案。** 按文档类型取舍内容，并将新的工程、安全与合规要求持续纳入模板。

### 3.2 结构化思维

**结构化思维：以事物的内在逻辑为基础，将无序信息组织成有序结构，降低复杂度与认知成本。** 相比零散堆砌的信息，概念精简、层次清晰、有规律的内容更易理解和记忆。

1. **定义问题**：明确要解决什么、读者需要得到什么结论，避免主题泛化。
2. **拆解问题**：将大问题拆成子问题，形成章节；每一节都服务于核心问题。
3. **整理归类**：合并同类内容，区分主次与层级，避免重复、遗漏和维度混杂。
4. **重塑表达**：按读者的理解顺序组织内容，结论先行，再用分论点、证据和图表支撑。

完成后回看：**全文是否回答了最初的问题？每一节是否必要，关键结论是否有依据？**

## 4. 回顾

**文档的价值不在于写了多少，而在于知识能否被理解、找到和持续使用。** 通过实践、分享与复盘形成团队知识网络，让经验不只停留在个人脑海中。
